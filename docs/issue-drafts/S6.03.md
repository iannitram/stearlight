labels: size:hard, kind:state, platform:windows, after-1.0

What: I want an allocation that imports a non-SHM resource with export allowed to be refused, or to import the resource, instead of silently getting memory backed by a fresh section. Today `shared_buffer` is true whenever `might_export` is set, and it ignores `res_info`. The host branch then runs with `shm_resource` NULL, so the import is skipped and the memory has no link to the resource the guest named.
Where: packages/windows-runtime/windows-venus/patches/0007-share-host-visible-buffers-through-windows-sections.patch:~158-170 (the `shared_buffer` definition and the host-memory branch condition at line 160) (code map: docs/code-map.md#windows-runtime)
Size: Hard (about 60 changed lines across the allocation path; C; Windows-only GPU memory import; real unknowns about whether guests send export plus a non-SHM import)
Serves: none (cleanup)
Done when: a test that imports a non-SHM resource with export allowed gets a clear error, or imports the resource, and never a fresh section. On a Windows VM run, bytes written through one context are visible through the imported allocation in another. The unknown about guest behavior is answered in the PR before the fix is chosen.

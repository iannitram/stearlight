What: I want RegisterAdvertisement to get the advertisement's properties without a blocking GetAll call to the client. The client cannot answer that call while it waits for its own RegisterAdvertisement reply, so the bridge stalls for 3 seconds, fails the registration, and holds its bus loop for that time. I found this by reading the code and have not reproduced it. An asynchronous call alone does not fix it, because the client is still blocked when the call is sent.
Where: packages/quest-runtime/linux/bluetooth-bridge.cpp:480 (`dbus_connection_send_with_reply_and_block` in the RegisterAdvertisement handler) (code map: docs/code-map.md#quest-linux-bridges)
Size: Hard (about 80 changed lines; C++; D-Bus; platform linux; the approach is an open design question)
Serves: M7
Done when: a client that blocks in its own RegisterAdvertisement call gets a registered advertisement, or a clean error, within 3 seconds. The bus loop is not blocked for that time, and the approach used (for example, taking the properties from the call or reading them after the reply) is written in the PR description. Checked on the Linux build host with two D-Bus clients: one blocks in RegisterAdvertisement while the bridge keeps answering a GetManagedObjects call from the other.

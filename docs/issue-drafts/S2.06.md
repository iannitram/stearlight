What: I want vkQueuePresentKHR to release `swap->lock` while it waits for the release fence. Today a stalled GPU also blocks vkAcquireNextImageKHR and vkWaitForPresentKHR on the same swapchain, because they take the same lock.
Where: packages/quest-runtime/linux/quest_wsi.cpp:330 (lock taken for each swapchain in vkQueuePresentKHR), :341 (offscreen fence wait), :362 (present fence wait) (code map: docs/code-map.md#quest-linux-bridges)
Size: Medium (about 50 changed lines; C++ Vulkan layer; platform linux)
Blocked by: S1.08
Serves: M4
Done when: no vkWaitForFences call in vkQueuePresentKHR runs while `swap->lock` is held. The state the function changes after the wait (released, presentIds, the frame counter, mirror state) is written under the lock again after the fence returns. Checked on a Quest 2: while one present waits on its release fence, a concurrent vkWaitForPresentKHR on the same swapchain returns on time.
